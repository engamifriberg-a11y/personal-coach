# פריסה: איך זה עולה לאוויר

שתי חתיכות, ולכל אחת מארח שמתאים לה:

| חתיכה | מה זה | מארח מתאים | למה |
|---|---|---|---|
| **האתר** (`/`, `/download`, `/transparency`, `/privacy`) | קבצים סטטיים | Vercel | CDN, HTTPS ודומיין בחינם; בדיוק מה שהוא טוב בו |
| **האפליקציה** (`/app` + `/api/*`) | תהליך Node + SQLite | Railway / Render / Fly | צריך תהליך שרץ קבוע ודיסק שנשמר |

אפשר גם להעלות **את שני החלקים ביחד** למארח אחד - השרת כבר מגיש גם את האתר וגם את
האפליקציה. זה המסלול הפשוט ביותר: דומיין אחד, בלי CORS, בלי לתחזק שתי פריסות.
Vercel נשאר רלוונטי אם רוצים את האתר על CDN מהיר ואת הדומיין הראשי שם.

---

## למה האפליקציה לא יכולה לרוץ על Vercel כמו שהיא

Vercel מריץ פונקציות ללא שרת: כל בקשה עשויה לקבל מכונה אחרת, ומערכת הקבצים נמחקת
בין בקשות. האפליקציה כותבת לקובץ SQLite על הדיסק, ולכן חשבונות, תוכניות ואימונים
היו נעלמים. זו תכונה של אירוח ללא שרת ולא תקלה.

מה שכן אפשרי שם, אם אי פעם תרצו: להחליף את שכבת הגישה לנתונים ל-Postgres מנוהל.
כל ה-SQL מרוכז ב-`src/db/repo.ts`, ולכן זו החלפה של קובץ אחד ונקודת כניסה serverless -
אבל זו עבודה אמיתית ובדיקה מחדש, לא הגדרה.

## מסלול 1: Railway (מומלץ)

### שלבים

1. **railway.com** ← New Project ← Deploy from GitHub repo ← `personal-coach`.
   Railway מזהה את ה-`Dockerfile` ובונה לפיו.
2. **Volume** (זה החלק הקריטי): בשירות ← Settings ← Volumes ← Add Volume,
   עם Mount path `/data`. בלי זה כל פריסה מחדש מאפסת את המסד.
3. **Variables** - להוסיף:
   ```
   SESSION_SECRET=<32 בתים אקראיים>
   ACCESS_CODE=<קוד הכניסה המהירה>
   NODE_ENV=production
   SQLITE_PATH=/data/coach.db
   TRUST_PROXY=1
   ```
   ליצירת הסוד: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
4. **Networking** ← Generate Domain. מתקבלת כתובת `*.up.railway.app` עם HTTPS.
5. **חשבון מנהל** - פעם אחת, מתוך Railway Shell או `railway run`:
   ```
   npm run seed
   ```
   ואז להתחבר ולשנות את הסיסמה מיד.

### חובה: עותק אחד בלבד

`railway.json` מגדיר `numReplicas: 1` במכוון. SQLite על volume ומגבלת הקצב שבזיכרון
התהליך לא עובדים נכון עם כמה עותקים במקביל. הגדלת מספר העותקים דורשת מעבר ל-Postgres
ולמאגר מגבלות משותף.

### עלות
Railway נותן קרדיט התחלתי, ואחריו התוכנית היא כ-5$ לחודש כולל volume.
**דיסק מתמיד אינו חינמי באף מארח רציני** - זה המחיר של נתונים שנשארים.

## מסלול 2: Render

`render.yaml` כבר בפרויקט, כולל הגדרת הדיסק:

1. **render.com** ← New ← Blueprint ← לבחור את המאגר. Render קורא את `render.yaml`.
2. להגדיר בלוח הבקרה את `SESSION_SECRET` ו-`ACCESS_CODE` (הם מסומנים `sync: false`
   ולכן אינם בקובץ).
3. Deploy.

### האזהרה החשובה ב-Render
**דיסק מתמיד זמין רק בתוכניות בתשלום.** בשירות בתוכנית החינמית האפליקציה תעבוד,
אבל כל פריסה מחדש או הערה-והתעוררות של השירות תמחק את המסד. `render.yaml` מוגדר
ל-`plan: starter` בגלל זה. אם משאירים `free`, להתייחס לזה כדמו בלבד.

## מסלול 3: Fly.io

מתאים למי שרוצה שליטה. בקצרה: `fly launch` (יזהה את ה-Dockerfile),
`fly volumes create coach_data --size 1`, ולמפות אותו ל-`/data` ב-`fly.toml`,
ואז `fly secrets set SESSION_SECRET=... ACCESS_CODE=...`.

## האתר ב-Vercel

1. **vercel.com** ← Add New ← Project ← לייבא את `personal-coach`.
2. Vercel קורא את `vercel.json`: פקודת הבנייה היא `npm run build:site`,
   והתוצר הוא `dist-site/`. אין תלויות להתקין.
3. **משתנה סביבה אחד** (Environment Variables):
   ```
   APP_URL=https://<הכתובת של האפליקציה ב-Railway>
   ```
   בזמן הבנייה, כל הקישורים "פתיחת האפליקציה" באתר יוצבעו לשם.
4. בלי `APP_URL`, הנתיב `/app` באתר מציג עמוד שמסביר שהאפליקציה רצה על שרת
   נפרד - במקום קישור שבור.

כל דחיפה ל-`main` תפרוס מחדש את האתר ואת האפליקציה, בשני המארחים.

### דומיין משלכם
נניח `example.co.il`:
- האתר: `example.co.il` ו-`www` → Vercel (Vercel ייתן את רשומות ה-DNS).
- האפליקציה: `app.example.co.il` → CNAME לכתובת של Railway, ואז
  `APP_URL=https://app.example.co.il` ב-Vercel.

## משתני סביבה

| משתנה | חובה | מה קורה בלעדיו |
|---|---|---|
| `SESSION_SECRET` | **כן** בייצור | הסשנים נחתמים בסוד פיתוח - פגיע |
| `SQLITE_PATH` | כן | ייכתב ל-`./data/coach.db` בתוך הקונטיינר, כלומר יימחק |
| `NODE_ENV=production` | כן | עוגיית הסשן לא תסומן `Secure` |
| `TRUST_PROXY=1` | כן מאחורי proxy | מגבלת הקצב תראה את כל הבקשות כאילו מכתובת אחת |
| `ACCESS_CODE` | לא | הכניסה המהירה כבויה; עובדים עם אימייל וסיסמה |
| `QUICK_ACCESS` | לא | ברירת מחדל `on` |
| `AI_PROVIDER` | לא | `none` - ניסוח מקומי, בלי עלות ובלי שליחת נתונים |
| `MEDIA_BASE_URL` | לא | הוראות כתובות במקום סרטונים |
| `PORT` | לא | המארח מזריק אותו בעצמו |

## בדיקה אחרי פריסה

```
curl -s https://<כתובת>/api/site-info          # צריך להחזיר JSON עם מספר התרגילים
curl -s -o /dev/null -w '%{http_code}\n' https://<כתובת>/app   # 200
```

ואז בדפדפן:
1. `/` - האתר נטען, שורת הזכויות בתחתית.
2. `/app` - מסך הכניסה. כניסה מהירה עם שם וקוד.
3. השלמת השאלון ← קבלת תוכנית ← התחלת אימון ← שמירת סט.
4. **פריסה מחדש, ואז התחברות שוב**: אם הנתונים שם - הדיסק המתמיד עובד.
   אם הם נעלמו - אין volume, וצריך לטפל בזה לפני שמכניסים אנשים.
5. התקנה על הטלפון (דורש HTTPS, שיש אצל כל המארחים האלה).

## גיבוי

אין מכניזם גיבוי מובנה. SQLite הוא קובץ אחד, ולכן:

```
sqlite3 /data/coach.db ".backup '/data/backup-$(date +%F).db'"
```

כדאי להריץ את זה בעבודה מתוזמנת ולהעתיק את התוצר אל מחוץ למארח.
מסד נתונים של בריאות שנמחק הוא לא תקלה שמתאוששים ממנה בהתנצלות.

## לפני שמכניסים אנשים אמיתיים

`docs/STATUS.md` מפרט את זה במלואו. בקצרה, מה שחוסם:

1. ביקורת מקצועית על 11 כללי בטיחות ותזונה ועל 57 התרגילים.
2. תנאי שימוש ומדיניות פרטיות שנכתבו על ידי עורך דין.
3. כיבוי הכניסה המהירה (`QUICK_ACCESS=off`) ומעבר לחשבונות מאומתים -
   קוד משותף אינו הוכחת זהות.
4. אימות אימייל ואיפוס סיסמה.
5. גיבויים וניטור.
